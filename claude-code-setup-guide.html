Setup Guide / Claude Code 環境移行

セットアップガイド

👤 対象: PM 個人の Claude Code 環境 📅 最終更新: 2026-09-04 📁 ソース: pm-skills / docs/setup-guide.md

新しい環境（新しい会社・新しい Mac）で、これまでの Claude Code 作業環境を再現するための手順書。

このリポジトリ（pm-skills）にはスキルとルールしか入っていない。スキルが動くための土台 — Claude Code 本体、プラグイン、MCP サーバー、外部 CLI、~/.claude/settings.json、メモリ — は環境側にあり、このガイドがその再現手順を担う。

前職固有の資産（社内プラグインマーケットプレイス、社内 MCP サーバー群、社内 CLI）は移行できない。該当箇所には代替の選択肢を書いてある。

0全体像

Claude Code 本体
  ├── ~/.claude/settings.json      権限・hooks・ステータスライン・有効プラグイン
  ├── プラグイン                    公式マーケットプレイスから 4 個
  ├── MCP サーバー                  Slack・課題管理ツール連携（要再構築）
  ├── 外部 CLI                      Confluence / Jira / Slack（要再構築）
  ├── ~/.claude/projects/*/memory/ リポジトリごとの永続メモリ
  └── pm-skills リポジトリ          スキル 26 個・ルール 6 個

所要時間の目安は、土台だけなら 1〜2 時間。MCP と CLI の再構築を含めると 1 日。土台が半分でも大半のスキルは動く（下表参照）ので、全部揃うまで待つ必要はない。

段階やることこれで動くようになるもの
段階 1（30 分）Claude Code・mise・pm-skills の clone文書系スキルのほぼ全部（PRD・リリースノート・マニュアル・清書・HTML 化）
段階 2（30 分）プラグイン・settings.json・ステータスライン仕様駆動の進め方、スキル作成支援、ブラウザ操作
段階 3（1 時間）Python パッケージ・音声入力pptx 生成、PLAN の音声ダンプ
段階 4（半日〜）MCP・外部 CLISlack 検索、Confluence 投稿、課題管理ツール連携

1基盤ツール

Claude Code 本体

ネイティブインストーラで入れる。

curl -fsSL https://claude.ai/install.sh | bash

~/.local/bin/claude にシンボリックリンクが張られ、実体は ~/.local/share/claude/versions/<version> に入る。~/.local/bin が PATH にあることを確認する。 

claude --version   # 2.1.201 以降を想定

初回起動でログインを求められる。個人の Claude アカウント（Pro / Max）か、会社が用意する組織アカウントのどちらかを使う。会社アカウントで入れる場合、作った資産の扱い（誰の著作物になるか）を先に確認しておく。 前職からの持ち出しで問題になるのはここなので、同じ問題を新職場でも作らないようにする。

自動更新は切っていた（autoUpdates: false）。破壊的変更で作業が止まるのを避ける意図。更新は自分のタイミングで claude update を打つ。

mise（ツールバージョン管理）

rulesync はリポジトリごとに mise.toml でバージョンを固定している。グローバルには入れない。

brew install mise

eval "$(mise activate zsh)"

音声入力（Typeless）

これは「あると便利」ではなく、仕事の質を決める要素。 plan.md に自分の考えを全部ダンプする工程は、キーボードでは量が出ない。10 分喋れば数千文字のコンテキストが入り、Claude が「勝手に生成した」内容にならなくなる。

Typeless を導入する。

CLAUDE.md に「ユーザーは音声入力を使うことがあるので、誤変換は文脈から補って解釈する」と書いておくと精度が上がる。

IDE

Claude Code は基本ターミナルで動かす。IDE（Cursor / VS Code）を開くのは次の場合に限定していた。

  • 大事な文書の細かい推敲
  • ディレクトリ構成や差分を丁寧に確認したいとき

ターミナルのウインドウを複数開いて並列に走らせるのが基本形。1 つの承認待ちの間に別の作業を進められる。

2pm-skills リポジトリの導入

前提：リモートを用意する

このリポジトリはリモート未設定の状態で作ってある（git remote -v が空）。持ち出し前に、個人アカウントの private リポジトリを作って push する。 

gh repo create pm-skills --private --source=. --push

~/.claude/settings.json の deny に Bash(git push*) を入れていた場合は外す（意図しない push を防ぐ安全弁として入れていたもの）。

push 前のチェック項目は docs/migration-checklist.md に残してある。

clone とセットアップ

git clone git@github.com:<自分>/pm-skills.git
cd pm-skills
mise install                      # rulesync を導入
mise exec -- rulesync generate    # .claude/ .cursor/ .agents/ CLAUDE.md AGENTS.md を生成

rulesync generate を実行するまで、Claude Code からスキルは見えない。.claude/ などの生成物は Git 追跡外なので、clone 直後は必ず実行する。

編集してよい場所

パス扱い
.rulesync/rules/ .rulesync/skills/ソースオブトゥルース。編集するのはここだけ
.claude/ .cursor/ .agents/ CLAUDE.md AGENTS.mdrulesync generate の生成物。直接編集しない
assets-external/バイナリ資産（テンプレート pptx・フォント）。.rulesync/ の外に置く

rulesync generate は .rulesync/ 配下のバイナリファイルを破損させる。pptx やフォントを .rulesync/ に置かない。これは実際に踏んだ罠。

編集後の自動生成を hook にする

.rulesync/ を編集したら毎回 rulesync generate を打つのは忘れる。プロジェクトの .claude/settings.json に PostToolUse hook を置いて自動化していた。 

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "bash -c 'fp=$(jq -r \".tool_input.file_path // empty\"); case \"$fp\" in */.rulesync/*|*/rulesync.jsonc) mise x -- rulesync generate ;; esac'"
          }
        ]
      }
    ]
  }
}

jq が必要（brew install jq）。

トークンの扱い

前職のトークンは 1 つも持ち込まない。

~/.claude.json には Slack のユーザートークンと Atlassian の API トークンが平文で入っている。新環境にファイルをコピーする形の移行はしない。退職時にこれらのトークンを失効させる（Slack はアプリの再インストールで無効化、Atlassian は API トークンを削除）。

新環境では各トークンを自分で発行し直す。設定の形だけを再利用する。

新職場での選択肢

目的選択肢
Confluence / 課題管理ツール公式の Atlassian リモート MCP サーバー（OAuth。トークンを平文で持たなくて済むので第一候補）。組織がリモート接続を禁じている場合は API トークン方式の stdio サーバーを自作
Slack公式 Slack MCP か、ユーザートークン方式の自作サーバー。検索（search_messages）・履歴取得・スレッド取得ができれば Slack 系スキルは動く
その他まず「その SaaS に MCP があるか」を調べる。なければ CLI か API を叩くスキルにする方が安定する

追加は claude mcp add、確認は対話中に /mcp。認証が必要なサーバーは /mcp から OAuth フローを通す。

MCP を増やしすぎない

MCP サーバーはツール定義がコンテキストを食う。「読み取りは MCP、書き込みは CLI」という切り分けが実運用では安定していた。Slack の検索は MCP、Slack への投稿は CLI（write-slack スキル）という構成になっているのはこの理由。

文書系のスキルは外部依存がほぼない。 つまり段階 1 のセットアップだけで、PRD → リリースノート → マニュアルという主要な流れは初日から回る。連携系は後回しでよい。

CLI が用意できないときの現実的な順序

  1. まず MCP で読み取りだけ通す（検索・取得ができれば調査系スキルが動く）
  2. 書き込みは手作業でコピペする（Confluence への貼り付け、Slack への投稿）。それでも生成部分が自動なので十分速い
  3. 頻度が高いものだけ、あとで CLI かスキルにする

「100% 自動化」を目指すと止まる。一番つらい部分だけ自動化する。

6~/.claude/settings.json

ユーザー全体の設定。以下は旧環境の構成から、環境依存の値を外した雛形。

{
  "permissions": {
    "allow": [
      "mcp__plugin_playwright_playwright__*",
      "Read(//Users/<user>/pm-skills/**)",
      "Write(//Users/<user>/pm-skills/**)",
      "Edit(//Users/<user>/pm-skills/**)",
      "Bash(git status*)",
      "Bash(git diff*)",
      "Bash(git log*)",
      "Bash(git add*)",
      "Bash(git commit*)",
      "WebFetch"
    ],
    "deny": ["Bash(git push*)"],
    "additionalDirectories": ["/Users/<user>/pm-skills"]
  },
  "hooks": {
    "Notification": [
      {
        "hooks": [
          { "type": "command", "command": "afplay /System/Library/Sounds/Glass.aiff", "async": true }
        ]
      }
    ]
  },
  "statusLine": {
    "type": "command",
    "command": "/path/to/ccsl",
    "padding": 0,
    "refreshInterval": 5000
  },
  "enabledPlugins": {
    "superpowers@claude-plugins-official": true,
    "skill-creator@claude-plugins-official": true,
    "plugin-dev@claude-plugins-official": true,
    "playwright@claude-plugins-official": true,
    "claude-code-setup@claude-plugins-official": true,
    "claude-md-management@claude-plugins-official": true,
    "frontend-design@claude-plugins-official": true
  },
  "theme": "dark",
  "effortLevel": "max"
}

権限設計の考え方

allow / ask / deny の三層で組む。判断の基準は「間違えたときに戻せるか」。

層入れるもの
allow読み取り・検索・調査系、ブラウザ操作、git status / diff / log / add。承認を求められると調査のテンポが落ちるものを入れる
ask破壊的なコマンド。rm 系、git の履歴を書き換える系（push reset rebase merge checkout restore clean revert stash など）
deny読ませたくないファイル（Read(.env) Read(.env.*)）。持ち出し前は Bash(git push*) も

additionalDirectories に作業リポジトリを列挙しておくと、リポジトリ外のファイルを触るたびの確認が減る。

設定を変えたら Claude Code を再起動する。 特に permissions と hooks はセッション開始時に読まれるので、起動中に書き換えても効かない。hooks は対話中に /hooks を一度開くと再読み込みされる。

WebFetch の許可はドメイン単位で指定する形（WebFetch(domain:example.com)）にもできる。広く許可すると意図しない外部送信のリスクが上がるので、業務データを扱うなら絞る。

hooks

イベント設定していた内容効果
Notification通知音を鳴らす（afplay）並列作業中に「承認待ち」に気づける。並列で回すなら必須
PostToolUse.rulesync/ を編集したら rulesync generate生成物の更新漏れを防ぐ
SessionStart / Stop / UserPromptSubmit状態ファイルの書き換えステータスライン等の外部連携用

「毎回 X したら Y する」という自動化は、メモリや CLAUDE.md に書いても実行されない。hook にしないと動かない。

ステータスライン

ccsl（Claude Code 用の拡張ステータスライン）を使っていた。トークン使用量・残量・コンテキスト消費が見える。

pip3 install ccsl
which ccsl   # このパスを settings.json の statusLine.command に書く

プロジェクト単位の設定

リポジトリ直下の .claude/settings.json（共有）と .claude/settings.local.json（個人・Git 追跡外）。旧環境では作業リポジトリ側で次のようにしていた。

  • settings.json（共有）: Read(.env) の拒否、rulesync generate の hook
  • settings.local.json（個人）: Bash(*) の許可 + 破壊的コマンドを ask、defaultMode: "acceptEdits"

defaultMode: "acceptEdits" は、ファイル編集を毎回承認せず自動で適用するモード。文書作成が主な作業だと承認回数が激減する。Git でバージョン管理されている前提でのみ使う。

7メモリ

Claude Code はリポジトリごとに永続メモリを持てる。

~/.claude/projects/<パスをスラグ化したもの>/memory/
├── MEMORY.md                    索引（毎セッション読み込まれる）
└── <memory-name>.md             1 ファイル 1 事実

各ファイルは frontmatter を持ち、type は user / feedback / project / reference のいずれか。MEMORY.md には 1 行のポインタだけを書く。

旧環境で溜まっていたメモリの例（内容は環境依存なので移行しない。何を書くべきかの型として使う）。

型例
承認方針「この種の操作は確認なしで実行してよい」— 調査系の出力、ブラウザ操作
ツール選択「この操作は MCP ではなく CLI を使う」（MCP 側に権限がないため）
コマンドの罠「課題の種別は英語名で指定する。日本語名だと 400 で失敗する」
既定値「特に指定がなければこの親フォルダ配下に作る」
復旧手順「権限エラーが出たらこのスコープを追加して再インストール」
リポジトリ運用「push 先は固定ブランチ」「push するのはスキルだけ」

新職場では空から始めて、ハマるたびに書かせる。「一度ハマったことに二度ハマらない」がメモリの唯一の役割。前職のメモリをコピーすると、存在しないツールや通らない手順を前提に動き出すので害になる。

CLAUDE.md との使い分けは、めったに変わらないことは CLAUDE.md、運用の細部はメモリ。旧環境の CLAUDE.local.md の冒頭にこの方針を明記していた。

症状原因と対処

10前職環境で最後にやること

新環境の構築とは別に、離れる側でやるべきこと。

  • 発行済みトークンを失効させる（Slack アプリ、Atlassian API トークン、その他 SaaS）
  • ~/.claude.json ~/.claude/settings.json を新環境へそのままコピーしない（トークンと社内パスが埋まっている）
  • スキルの持ち出しについて会社の確認を取る（在職中に業務として作ったものは原則として会社の成果物）
  • このリポジトリを個人の private リポジトリへ push する（docs/migration-checklist.md のチェック項目を先に消化する）
  • 同梱フォントのライセンスファイルを配置する（Apache 2.0 は頒布物へのライセンス同梱を条件にしている）
